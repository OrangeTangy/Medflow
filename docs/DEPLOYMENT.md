# Production deployment

The private Sites app is a fictional workflow sandbox. Deploy the Python/PostgreSQL runtime to your hospital’s approved cloud/network for live operations. No cloud account, hospital OIDC tenant, network hardware, or approved transcription provider was supplied in this session; those integrations are not deployed by this repository.

## Database and identities

1. Create a private PostgreSQL 16 database, a migration-owner login, an application login, an authentication login, and a worker login. Use independent randomly generated credentials in a secrets manager. Apply Alembic with the migration owner: `cd backend && alembic upgrade head`.
2. Run `infra/roles.sql` once as the owner; grant each login only its named group role. The web app login must not own tables or have BYPASSRLS. The auth login intentionally bypasses user RLS but has grants only for user/identity/session lookup. The worker is a trusted cross-organization processor, isolated from public traffic. Store their connection URLs separately.
3. Set `DATABASE_URL`, `AUTH_DATABASE_URL`, and `WORKER_DATABASE_URL` for their respective processes. Use `sslmode=verify-full` and the approved CA against managed PostgreSQL. Use TLS for managed Redis (`rediss://`). Do not expose DB/Redis ports publicly.
4. Configure the exact HTTPS `PUBLIC_ORIGIN`, OIDC issuer/client/secret, a random ≥32-character `SESSION_SECRET`, and the identity provider’s MFA AMR/ACR value. Register `/api/auth/callback` as the redirect URI. Hospital IdP policy should require MFA; the API also verifies it. SAML federation can terminate at the OIDC identity broker; native SAML assertion handling is not included.
5. Provision an administrator with migration-owner credentials: `python -m app.provision --organization 'Hospital name' --name 'Administrator name' --email admin@example.org --subject 'verified-idp-subject'`. No self-registration or automatic first-user admin is enabled. Application doctors are added by this administrator and matched by exact issuer/subject.

The first migration contains the normalized schema, tenant foreign keys, forced RLS, and a GiST exclusion constraint. Never edit an applied migration. Add a new revision for every later schema change. The migration owner must remain separate from runtime logins.

## Containers and AWS

Build the two Docker images. Run the web gateway/API, workers, and one scheduler using `docker-compose.yml` or ECS Fargate. The local gateway is bound to `127.0.0.1:8080`. Terminate TLS at an approved load balancer; set the public origin to that exact URL and trust proxy headers only from your private load-balancer CIDR.

Recommended AWS topology: private ECS tasks in two availability zones, internet-facing HTTPS ALB/WAF, encrypted Multi-AZ RDS PostgreSQL with PITR, TLS ElastiCache Redis, private S3 with KMS, Secrets Manager, CloudWatch logs/alarms, ECR image scanning, and AWS Backup. Grant API/worker S3 permissions only to the organization audio prefix and KMS encryption context. Block all public bucket access. Apply a temporary-audio lifecycle expiration independent of worker success.

ECS web service task contains containers named `api` and `web`; workers and scheduler are separate services. Inside a shared Fargate task the gateway upstream must be `127.0.0.1:8000` (adjust `infra/nginx.conf` from its Compose service hostname `api`). Keep scheduler desired count one. Expose only gateway port 8080. Containers run without privileged access; application API uses a non-root UID. Make logs redact cookies, Authorization headers, transcripts, identity subject values, and audio keys.

CI runs unit/API/PostgreSQL-RLS tests, frontend builds, and dependency scans. `.github/workflows/deploy.yml` is an OIDC-based ECS promotion workflow for an existing reviewed infrastructure deployment. Configure the named GitHub production environment variables. `scripts/deploy-ecs.py` preserves current task roles/networking/secrets, builds immutable SHA tags, runs a migration with the **separate migration DB secret**, promotes all three services, waits for stable health, and restores prior task definitions if stabilization fails. Use backward-compatible expand/contract migrations so an application rollback remains possible.

`npm run package` produces the Sites-only Worker artifact, including the compiled Next static shell and isolated sandbox API. Its D1 migration stores only owner-scoped fictional data. It must not be repurposed as a hospital deployment by changing a label.

## Runtime checks

`/health/live` verifies the process; `/health/ready` checks PostgreSQL/Redis. `/metrics` is administrator-protected; scrape with an approved authenticated collector. OpenAPI is generated by FastAPI. Configure alerting for readiness failures, HTTP errors, accounting silence, outbox age/failures, retention job failures, authentication failures, and database capacity. Logs and metrics must not contain operational transcript contents.

Before routing live staff, execute all acceptance tests in `ACCEPTANCE.md` and record the named reviewer approvals. Deployment automation does not substitute for this review.
