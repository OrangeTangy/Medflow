# Status against the original hospital specification

Assessment of source at the 2026-11-02 handoff. **The complete original specification is not finished or production-certified.** A functional WiFi logging/notification pilot and broader enterprise implementation are included. Code existence, configured integrations, and a validated production deployment are separate states.

| Requested capability | Delivered behavior | Remaining work / boundary |
| --- | --- | --- |
| WiFi connect/disconnect on your own network | Android foreground monitor, native desktop watcher, exact-SSID pairing, local outboxes, receiver and stored notifications | Test actual phones/OS permissions, roaming, battery/sleep and site routing. An SSID alone does not identify a doctor; use one pairing/enrolled identity per device. |
| Automatic hospital network attendance | Signed RADIUS/normalized-event adapter interface, enrollment, raw events, processing jobs and UTC reconciliation source | No hospital hardware is connected. Cisco/Aruba/UniFi equipment-specific adapters and EAP-TLS/RADIUS configuration need actual deployment details and validation. |
| Arrival/departure timestamps and duration | Local manual arrival/departure commit to SQLite; enterprise session reconciliation handles trusted evidence | Phone/paired SSID logs remain unverified and **do not generate attendance sessions/hours**. Manually record attendance in the local pilot. |
| Accuracy and uncertainty | Reconciliation code/tests cover duplicates, out-of-order events, grace, roaming, multiple-device union, stale evidence, DST and unknown gaps | Hardware event semantics and real outages must be validated. Polling may miss short changes; a connected device does not prove work or personal presence. |
| Doctor/admin permissions | Server-enforced own-record/organization scoping; local password accounts; PostgreSQL forced RLS in enterprise schema | Local SQLite has no RLS and trusts its OS account. No doctor should have direct DB/filesystem credentials. Deployment identity provisioning/penetration testing remain required. |
| Authentication, SSO and MFA | Local hashed passwords for the pilot; OIDC PKCE and MFA-claim checks in enterprise source | No live IdP tenant is configured here. Local accounts do not have enterprise MFA. Native SAML handling is absent; use an approved federation broker. |
| Activity text and history | Saved/editable activity reports, categories, timestamps, review and doctor/admin history | The local console uses text entry. Speech-related workflows require the larger UI and, for transcription, approved services. |
| Voice capture and speech-to-text | Next.js UI has recording, pause/resume/playback; enterprise upload, private audio storage and asynchronous transcription integration code | No approved medical transcription provider is configured. Local automatic transcription is disabled. Uploads are limited to 25 MB; streaming/chunked long-form assembly and demonstrated medical-vocabulary accuracy are not included. |
| Optional AI summaries | Approval-gated endpoint and editable, source-traceable categorization logic | Provider/agreements must be configured and validated; disabled in local mode. No clinical/PHI service is approved by default. |
| Visual dashboards and reports | Larger Next.js doctor/admin dashboards, daily records, weekly charts, location distribution, date selection, individual timelines, CSV/PDF source | Build the larger UI separately. Dedicated monthly/annual heatmaps, average arrival/departure statistics and rich arbitrary-range reporting remain extensions. The Python-only page is a simpler console. |
| Corrections and administration | Correction/review APIs and larger UI workflows; doctor add/disable, profiles, locations/networks, review and audit access | The simple console exposes a smaller subset. Enterprise invitations/email and workforce-consent acknowledgment collection require integrations. |
| Real-time notifications | Durable paired device notifications, polling feed, opt-in browser desktop alerts; enterprise SSE/update source | Browser page must stay open. No email, SMS or closed-browser push. Offline devices deliver after a route returns; mobile data alone cannot reach a private-LAN-only receiver. |
| Persistent data and migrations | SQLite for local use; normalized PostgreSQL/SQLAlchemy/Alembic schema with tenant constraints and indexes for enterprise | Each mode has separate storage/auth assumptions. Local records are not automatically migrated into a hospital's production tenant. |
| Multiple organizations and thousands of doctors | Enterprise organization scoping, PostgreSQL RLS, Redis/Celery/outbox and multi-process deployment source | No thousands-user load benchmark; retained-history replay needs checkpoints/partitioning for large histories. Local SQLite is not the scalable multi-hospital deployment. |
| Deployment, monitoring and recovery | Docker/Compose, CI, ECS promotion source/configuration, audit/metrics, local backup command | Hospital AWS/other infrastructure, TLS, secrets, alerts, operational backup schedules and a real restore exercise require deployment. The optional hosted Sites app is a fictional sandbox. |
| Retention, security and compliance | Session/origin/rate-limit controls, private audio paths, provider gates, retention maintenance source and administrative acceptance document | No HIPAA compliance claim. Workforce data retention is policy-controlled; local paired logs have no automatic backend purge. Approve laws/notice/consent, agreements, residency and incident procedures before real workforce use. |
| Mobile/PWA | Responsive web UI/PWA shell; native Android WiFi test APK | No native iOS collector. A browser/PWA cannot reliably monitor background WiFi association. Android APK is a debug/test distribution, not a production signed mobile rollout. |
